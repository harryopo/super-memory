# 变更影响矩阵

某类变更一旦发生，要同步动哪些层。看新事实**波及哪些文档**，不是只看这次多了什么。

## 常见模式

| 变更 | 波及位置 |
|---|---|
| 新增 API / 路由 | 规则文件路由清单 · integration-guide · architecture 的 Routes |
| 新增 / 改名环境变量 | 规则文件环境变量表 · runbook · 下游 integration-guide |
| 新增数据库表 | 规则文件 · architecture 的 Data Model |
| 新增跨多文件的大特性 | 以上全部 + architecture 新章节 + handoff 已完成清单 |
| 新增大能力（一整套） | 下面四处都要补 |
| 跨项目改动 | 上下游两边 docs **都要对齐**，尤其是接口/协议/SDK 说明 |
| 记忆层变化 | 相对时间→绝对日期；过期事实→改掉；重复→合并；已完成待办→隔离 |

## 新增一个能力，文档变更通常要落四处

1. **integration-guide**（或对应"外部视角"文档）：怎么用 —— curl / SDK 示例 / 错误码表
2. **architecture**：怎么工作 —— 数据流、状态机、设计取舍
3. **runbook**：怎么运维 —— 冒烟命令、故障排查、依赖的环境变量
4. **handoff / 项目变更记录**：已完成清单

API 速查表、环境变量表、术语表是高频查阅的结构化信息，**必须保持"所见即最新"**。

## 跨项目检查

本次会话改了项目 A，且项目 B 依赖 A → B 的 docs 也要改。历次同步最常漏的就是这条。
不要假设"一个项目的 docs 改了就够了"。
