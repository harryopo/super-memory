# 三层沉淀与知识归属权威

一套项目里同时存在五个知识落点。不划清归属，同一条事实会在两处漂移成两个版本。**每条知识有唯一的家，其他位置只放索引。**

## 三层时间尺度

| 层级 | 载体 | 内容范围 | 更新频率 |
|---|---|---|---|
| 短期会话记忆 | 当前对话上下文 | 临时调试过程、中间尝试、局部变量细节 | 会话内，**不落盘** |
| 中期交接记忆 | `.ai/HANDOFF.md` | §0 当前快照（刷新式）+ 进度/断点/经验/下一步编年（追加式） | 每次会话结束/暂停必更 |
| 长期项目记忆 | `.ai/knowledge/` | 通用解法、技术决策、代码模式、业务规则、踩坑库 | 符合入库标准时同步 |

## 五处落点的归属权威

| 落点 | 只放什么 | 不放什么 | 谁负责写 |
|---|---|---|---|
| `.learnings/` | **未升档的实时暂存**：错误、纠正、知识缺口、特征请求，含未验证推断 | 已验证且通用的结论（已升档，只留指针） | capture |
| `.ai/HANDOFF.md` | 当前进度、断点、本次经验、下一步、运行验证、禁区；长期库内容只做索引引用 | 已固化的通用方法论全文 | handoff |
| `.ai/knowledge/` | **项目内长期权威**：跨模块通用解法、架构与选型决策、可复用模式、业务规则、开发规范 | 未验证内容（`[W]``[Q]``[R]` 不进）、单会话进度流水 | handoff 升档 / promote |
| agent 记忆库（宿主目录，两级） | 跨会话的**个人偏好、协作习惯、用户背景**；跨项目的工具用法 | 项目内部的技术决策与业务规则 | save |
| 项目规则文件（`CLAUDE.md`/`AGENTS.md`） | **硬边界**：禁止事项、红线、命令速查、权限模型、协作流程 | 历史叙事、详细机制、单次事故复盘 | promote |

判据一句话：

```
只对本项目成立？
├─ 是 → 会不会被别的模块复用？
│        ├─ 会 → .ai/knowledge/（长期权威）
│        └─ 不会 → .ai/HANDOFF.md（进度/断点）或 .learnings/（暂存）
└─ 否（跨项目都成立）→ 是"人和人怎么协作"的偏好？
         ├─ 是 → agent 记忆库·用户级
         └─ 否 → 是必须每次看到的硬规则？ → 规则文件
                 否则 → agent 记忆库·用户级
```

升档方向固定单向：`.learnings/` → `.ai/knowledge/` → 规则文件。低层留指针标"已升档"，高层不回抄低层全文。

## `.ai/knowledge/` 五分类

目录**按需创建**——只建本轮真有内容要写的分类，文件按项目实际语言/模块命名，不预铺空骨架。**新建分类或新文件时**，同步在 `.ai/knowledge/README.md`（若存在）登记一行（`文件名 → 一句话用途`），让索引跟上写入。

| 分类 | 放什么 | 命名按项目实际 |
|---|---|---|
| `decisions/` | 架构决策、技术选型、协议与规范决策 | 如 `architecture.md`、`storage.md` |
| `patterns/` | 可复用代码与设计模式 | 前端项目才写 `frontend.md`，CLI 项目写 `cli.md` |
| `problem-solutions/` | 踩坑与标准解法 | 如 `environment.md`、`dependency.md` |
| `business/` | 核心业务规则与领域知识 | 无业务逻辑的工具项目**不建**这一类 |
| `standards/` | 编码规范、提交规范、验证规范 | 已由规则文件承载的只放指针 |

## 入库标准

符合任一条件**必须**沉淀到长期库：

- 跨模块、跨场景通用的解决方案
- 影响全局架构与技术栈的决策
- 可复用的代码模板、设计模式、工具函数
- 核心业务规则与领域约束
- 高频出现的典型问题与标准解法
- 项目级开发规范与流程约定

不符合的（单次事故复盘、临时进度、未验证推断）留在低层，不进长期库。

## 条目格式

```markdown
## [K-YYYYMMDD-NNN] <一句话说清这条是什么>

**置信度**：[V] | [F]　　**生效**：YYYY-MM-DD　　**记录**：YYYY-MM-DD　　**最后验证**：YYYY-MM-DD　　**适用版本**：<范围或"当前 main">

**适用场景**：…　　**不适用**：…
**结论**：…
**根因/权衡**：…
**锚点**：`path/to/file.ts:42`、commit `abc123`
**来源**：HANDOFF §5.2（YYYY-MM-DD 会话） / `.learnings/LRN-…`
**Tags**：部署 rsync deployment　（2–4 个检索词：中文词 + 英文词 + 领域词，供换词命中与排序检索）
**Related**：K-…、K-…　（确无相关条目写"无"，不许留空）
```

**溯源必填**：每条回指原始交接记录或 `.learnings/` 条目 id 与代码提交，否则下次没法判断它是否还成立。

**编号（NNN）**：当天已入库条目数 + 1，用命令算，不许随机（与 capture 的 ID 规则同规）：

```bash
D=$(date +%Y%m%d)
N=$(($(grep -rhE "^## \[K-$D-[0-9]+\]" .ai/knowledge/ 2>/dev/null | wc -l) + 1))
printf 'K-%s-%03d\n' "$D" "$N"
```

**双时间戳**：`生效` = 事实在现实中的起点（决策拍板日、修复合入日）；`记录` = 本条写入或最近改写之日。二者分离即弱化版 bi-temporal——判断"结论还成立吗"看生效 + 最后验证，判断"当时是不是最新认知"看记录。同一天就填同一天，不许省略字段。

**Related 互链**：入库前 grep 1–2 个关键词检索相关旧条目，新旧双向写 `Related`。旧条目因互链需要**小幅补充**时允许只加一行（登记日期），不算改写历史；需要改结论的走下面的 SUPERSEDE。

**失效标记（SUPERSEDE 时）**：**置信度字段保留原值不动**，另起一行写（`[已失效]` 是合法第六态，memory-doctor 检查三认它）：

```markdown
**置信度**：[V]　　**生效**：2026-10-03　　**记录**：2026-10-03　　**最后验证**：2026-10-03　　**适用版本**：当前 main
**已失效**：2026-10-10 起由 K-20261010-002 取代（原因：框架中间件统一处理，自建方案废弃）。本条原地保留归档，不再推荐复用。
```

三要素缺一不可：**日期 + 取代者 ID + 原因**。不删除、不隔离、不改写原正文。

## 巩固四操作

任何条目写入长期库前，先 `grep` 相似旧条目，然后**四选一并写明判了哪条**（对应 mem0 的 ADD/UPDATE/DELETE/NOOP，DELETE 按本项目"只降级不删除"铁律替换为 SUPERSEDE——**原地留档，不隔离**）：

| 操作 | 条件 | 动作 |
|---|---|---|
| ADD | 无相似条目 | 新建（含全部格式字段 + Related 互链） |
| UPDATE | 同主题但旧条目过时/不全，新结论是其延伸 | 改旧条目，**保留原 ID 与来源链**，正文加一行更新记录（绝对日期 + 改了什么） |
| SUPERSEDE | 新结论推翻旧结论 | 旧条目按「失效标记」写法标 `[已失效]`（日期+取代者+原因），**不删除**；新条目 Related 回指旧条目 |
| NOOP | 完全等价 | 不写，只在旧条目 Metadata 递增 Recurrence / 补 See Also |

触发点：handoff A3（升档）、promote 写入 `.ai/knowledge/` 时、neat 合并重复条目时。判定写进变更摘要，"新增了一条"必须说明为什么不是 UPDATE/SUPERSEDE。

## 有效性维护

- **时效标记**：`最后验证` 与 `适用版本` 必填；agent 记忆库条目鼓励在 frontmatter 加可选 `last_verified: YYYY-MM-DD`
- **超龄提示**：带 `last_verified` 的记忆条目超 90 天未验证 → neat 盘点时逐条列出"建议重验或降级"（附重验方式），**不代判、不删除、不静默跳过**
- **定期校验**：架构重构、依赖升级、业务变更后，相关条目必须重新核验；核验不了就降置信度并在正文写明
- **淘汰**：过时/废弃条目改标 `[已失效]` + 原因 + 替代，**原地保留归档、不删除、不隔离、不再推荐复用**（区别于 agent 记忆库废弃条目——后者才走隔离）
- **禁止**：物理删除长期库条目、改写历史版本记录
